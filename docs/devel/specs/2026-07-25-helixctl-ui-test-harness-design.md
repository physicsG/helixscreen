# helixctl UI Test Harness — Design

**Date:** 2026-07-25
**Status:** Design approved, not yet implemented
**Branch:** `feature/ui-test-harness`

## Problem

HelixScreen has no automated coverage of the running application. What exists:

- **In-process Catch2 UI tests** (`LVGLUITestFixture` + `tests/ui_test_utils.h`) — real, but they
  build widgets in isolation inside the test process. They cannot exercise app lifecycle,
  the navigation stack, panel teardown, or async population. Some panels have no safe
  in-process lifetime at all: `PrintStatusPanel` dangles the XML subject registry when
  stack-local and dangles `ObserverGuard`s on later `PrinterState` deinit when a singleton.
- **tests/integration/test-navigation.sh** — 21 lines that run the app for 10 seconds and
  print "You should manually test clicking the icons in the UI!"
- **`docs/images/`** — 68 screenshots generated by `scripts/screenshot-all.sh`. Regenerated,
  never compared.

Meanwhile `helix-screen ctl` (see `HELIXCTL.md`) can already navigate, click, set values,
scroll, introspect geometry, read subjects, and capture screenshots against a live instance
with the real widget lifecycle. It is the missing test harness, one `--json` flag away from
being scriptable.

## Goals

Ranked by why this is being built:

1. **Verification harness.** A scripted replacement for the manual "launch it, drive it, read
   the log" loop. Runs on demand, fast to author, fast to re-run.
2. **Visual regression.** Golden screenshots for a corpus of screens, diffed on change.
3. **CI regression gate.** Useful, secondary. Constrained by golden portability (see Risks).
4. **Crash/soak hunting.** Out of scope for now; the primitives below are chosen so it can be
   added later without redesign.

Out-of-process driving also sidesteps the in-process lifetime problems above by construction —
the process boundary is the isolation.

## Non-goals

- Replacing the Catch2 unit tests. Those stay where they are and cover what they cover.
- Testing on-device. The remote-control subsystem is compiled out of release builds
  (`HELIX_ENABLE_REMOTE_CONTROL`); dev images can opt in, but this harness targets native.
- Assertions in the wire protocol. The server exposes capabilities; the harness holds policy.

## Determinism model

A screen is not stable when animations stop. It is stable when the async work lands — the
thumbnail decoded, the gcode geometry built, the first status frame arrived. This is the
actual source of screenshot-suite flakiness, and pinning the clock does nothing for it.

Determinism therefore has two independent halves.

### Freeze — stop the moving parts

One `freeze` command combining:

- `lv_anim_delete_all()` to stop animations already running.
- `animations_enabled = 0` to prevent new ones — an existing setting honored at 51 call sites.
  **This must not go through `DisplaySettingsManager::set_animations_enabled()`**, which calls
  `config->save()` and therefore writes the change to `settings.json` on disk. `freeze` is a
  transient test-mode action; persisting it means a `--remote` dev instance that is killed or
  crashes between `freeze` and `unfreeze` leaves the user's real config with animations
  permanently disabled. Set the subject directly, or add a non-persisting setter for this
  case. Automated tests are insulated by the `settings-test.json` split, which is exactly why
  this would not have surfaced in testing.
- Pausing periodic timers individually, **with a skip list** (see below); the codebase has 85
  `lv_timer_create` sites driving repaints.
- Pinning the simulated clock.

**The global `lv_timer_enable(false)` is not usable here, despite being the obvious lever.**
`UpdateQueue`'s processor is itself an `lv_timer` (`ui_update_queue.h:108`), and
`RemoteControlServer::execute_on_ui_thread` dispatches every handler through
`helix::ui::queue_update`. Disabling timers globally therefore stops the update queue, and
every subsequent ctl command — `unfreeze` included — blocks for the 10s UI-thread timeout and
throws. Freeze would brick the control channel it was issued over.

Timers are instead paused individually by walking `lv_timer_get_next(NULL)` and calling
`lv_timer_pause()` on each, skipping exactly two:

1. `UpdateQueue`'s processor, or the control server cannot dispatch.
2. The display refresh timer (`lv_display_get_refr_timer()`), or nothing renders and the
   frame-hash gate never observes a new frame.

`unfreeze` reverses all of it, resuming the set of timers it paused — tracked as a vector of
`lv_timer_t*` on the server so it never resumes a timer it did not pause. A launch flag is
deliberately not added; if boot-time nondeterminism proves to be a problem in practice, one
can follow.

### Settle — know when async work finished

`wait_idle [--timeout N]` blocks until `UpdateQueue` pending is 0 and `HttpExecutor` in-flight
is 0 on both lanes, held stable across two consecutive samples. `UpdateQueue` has the size
internally but no public accessor; `HttpExecutor` has no in-flight count at all. Both are
small additions.

**Animations are deliberately NOT counted**, though an earlier draft of this design included
`lv_anim_count_running()`. A real UI has legitimately perpetual animations, so "zero
animations running" is not a reachable idle state in general — it is a property of a
particular screen and a particular settings configuration, not of the app having finished
its work. Implementation found this concretely: `print_file_detail`'s loading spinner lives
inside the eagerly-built `print_select_panel`, so its three infinite animations run from boot
onward regardless of which screen is displayed. Counting animations made `wait_idle` succeed
only when the `animations_enabled` setting happened to be off, which is a configuration
accident rather than a contract.

Animation-driven pixel churn is covered instead by the frame-hash screenshot gate below,
which measures the thing that actually matters for a capture — whether the pixels stopped
changing — rather than inferring it from an animation count.

Separately, that spinner should not animate while it is invisible: an eagerly-built widget
burning three animation timers forever is wasted CPU on the smallest devices we ship to.
That is a real defect on its own merits and independent of the determinism contract above —
but it is **not fixed here**. Two attempts were made and both reverted:

1. Gating `ui_spinner`'s animation start on `animations_enabled`, matching every other
   decorative animation. Rejected on review: `animations_default()` resolves to
   `caps.supports_animations`, which is false for EMBEDDED and BASIC platform tiers
   (`platform_capabilities.cpp:78,84`) — the exact devices this was meant to help. It would
   have frozen every loading spinner in the app on AD5M/K1/SonicPad permanently, which reads
   as hung, not idle.
2. A visibility-based gate: start the animation on `LV_EVENT_DRAW_MAIN_BEGIN` (a widget only
   gets this when LVGL actually renders it, which requires it and every ancestor to be
   non-hidden), self-stop inside the running animation's own `exec_cb` via `lv_obj_is_visible()`
   (calling `lv_anim_delete()` from inside an exec_cb is an LVGL-supported pattern —
   `anim_timer()` explicitly detects list mutation and restarts from the head — so this part
   isn't the problem). Reverted because `LV_EVENT_DRAW_MAIN_BEGIN` was empirically confirmed,
   via a temporary `lv_anim_count_running()`/`stop_if_hidden()` instrumentation, to **never
   fire** on this widget even when it was genuinely visible on screen (subject-flipped from
   hidden to shown, modal left open, no draw-begin observed) — meaning the animation would
   never (re)start at all. Root cause not identified before the revert; plausibly LVGL 9's
   dirty-rectangle redraw only sends `DRAW_MAIN_BEGIN` to objects within an invalidated
   region on a given frame, and un-hiding via the `bind_flag_if_eq` binding may not be
   invalidating the area the way a direct `lv_obj_remove_flag()` call would.

The CPU-waste defect remains open. A future fix needs to verify the chosen start/stop
mechanism actually drives the animation on a real visible spinner (not just assume the event
fires) before landing.

`wait_idle` is best-effort by design, because the enumeration surface is large and grows. A
scan of the codebase found these sources it cannot see:

| Source | Where | Note |
|---|---|---|
| Raw `lv_async_call` | `panel_widget_manager.cpp:923` (home-panel widget-gate rebuild), `ui_nav_manager.cpp:157` (overlay-close), `ui_filament_path_layers.cpp`, `grid_edit_mode.cpp` | LVGL exposes only call/cancel — **no count API** (`lv_async.h:44,51`) |
| Thumbnail render thread | `gcode_object_thumbnail_renderer.cpp:58` | Own `std::thread`, not `HttpExecutor` |
| GCode geometry build | `ui_gcode_viewer.cpp:186` (`build_thread_`) | Same |
| GCode layer/streaming | `gcode_layer_renderer.h`, `gcode_streaming_controller.h` | Same |
| Mock backends | `moonraker_client_mock.cpp:3639` (`simulation_thread_`) + 3 timers, `moonraker_client_mock_print.cpp` (2 timers), `ams_backend_mock.cpp` (6 threads), `wifi_backend_mock.cpp` (2) | Mock mode **adds** nondeterminism |
| Deferred deletion | 210 `safe_delete_deferred` / `lv_obj_delete_async` / `safe_clean_children` sites | Escapes the queue by design — `pending == 0` does not mean the old subtree is gone |

The rejected alternative was an `AsyncWorkRegistry` RAII token held by every UI-affecting
async producer, making `wait_idle` a hard guarantee and lintable the way
`scripts/check_l081_anti_pattern.py` is. It was rejected because its value depends on being
*complete*: a registry with three gaps is a guarantee that cannot be trusted, which is worse
than an honest best-effort. Tokens will be added to individual producers — the thumbnail
renderer and gcode builder first — only when those specifically flake.

### Screenshot gate

The two failure modes are complements. Freeze removes the perpetually-animating widget that
would stop a frame-hash from ever settling; the frame-hash covers the enumeration gaps that
`wait_idle` cannot see. So the capture path is:

```
freeze → wait_idle → require 3 consecutive identical frame hashes → capture
```

exposed as `screenshot --stable`.

### Known gap: the stability check and the capture are not atomic

`handle_screenshot` (`remote_control_server.cpp:594-668`) does the stability loop
and the final capture as **two separate `execute_on_ui_thread` round trips**: the
loop (lines 619-649) samples `frame_hash` until 3 consecutive samples match, then a
fresh, independent call (line 651) does its own `capture_frame()` — it does not
reuse the buffer from the last verified-stable sample. There is a real gap between
"verified stable" and "captured" during which nothing prevents a repaint.

This was investigated as a suspected cause of golden-capture non-reproducibility
under machine load and **ruled out**. A controlled A/B — identical freeze +
double-capture logic, identical heavy CPU load (32-core box oversubscribed to
~50-60 busy processes), the only variable being which screen was targeted — showed
Home failing (captured a 25.9°C vs 26.1°C temperature-label mismatch, tracing to
`moonraker_client_mock.cpp`'s `temperature_simulation_loop`, a perpetual sine wave
on a background thread invisible to `freeze()`) while Settings passed 20/20 under
the same load. The gap exists structurally, but it isn't what was causing the
observed failures.

Why it's currently harmless: **every golden screen is static by construction** —
"does the screen ever repaint on its own" is exactly the selection criterion the
corpus already applies (see "Initial corpus" below and `test_screens.py`'s
deferred-screens list). With nothing changing on the screen, the gap has nothing to
catch mid-change, regardless of how wide load makes it.

The condition under which it *would* matter: golden-ing a screen with any
self-driven repaint — live telemetry, a free-running spinner, wall-clock content,
anything the mock backend or LVGL itself updates without the test driving it. That
is precisely the category the corpus selection rule already excludes. The gap stays
harmless as long as that rule holds; it becomes live the moment someone goldens an
animated screen and assumes `--stable` makes it safe anyway. A real fix, if one is
ever needed, is to capture the frame *inside* the same UI-thread call that confirms
the last stable sample, rather than a second round trip — not done here, since there
was nothing to fix it against.

## helixctl additions

### Tier 1 — required

| Command | Behavior |
|---|---|
| `--json` | One-shot client flag. Emits the raw JSON-RPC `result` as one line on stdout, nothing else. Errors go to stderr as the `error` object and the process exits non-zero, so `set -e` and `subprocess.run(check=True)` both work without inspecting the payload. Ignored by the REPL. |
| `wait_idle [--timeout N]` | Structural quiescence, above. |
| `freeze` / `unfreeze` | Determinism toggle, above. Note the skip list — a naive global timer disable deadlocks the control channel. |
| `screenshot --stable [--target <w>]` | Frame-hash gate folded into capture. `--target` crops to a widget's bounding box. |
| `text <target>` | Read a label's text. Currently impossible — `ls` entries carry `name`, `path`, `layer`, `type`, `actions`, and `value` for switches/sliders/dropdowns/textareas (`remote_control_server.cpp:1364-1375`), but the only text extraction anywhere in the server is `lv_textarea_get_text` at line 1359. |
| `reset` | Pop all overlays, dismiss modals and toasts, return to home. |

`--target` on screenshot is what keeps the golden corpus maintainable. A widget-scoped golden
changes only when that widget changes; a full-screen golden goes red when anything anywhere on
the screen moves, which is how a suite trains its owner to blanket-accept diffs.

`reset` is the alternative to booting per test. At roughly 2s a boot, 100 goldens is 200s of
pure startup. Per-boot remains available as the fallback for a test that dirties global state.

Note that `get_value` is **not** needed — `ls <target>` already returns `value` for every
value-control type.

### Tier 2

| Command | Behavior |
|---|---|
| `press <key>` | Send a key event (ENTER/ESC/arrows). Needed for encoder-nav devices and keyboard flows that `click` cannot reach. |
| `toasts` | List active toasts. Transient and easy to miss in a golden; a common assertion target. |
| `set_clock <epoch>` | Pin to a specific timestamp rather than just freezing at whatever "now" was. |

### Tier 3 — deferred

Socket transport in the Python client (only if soak-test throughput demands it), and
`AsyncWorkRegistry` tokens for the thumbnail renderer and gcode builder (only on observed
flakes).

## Harness

Python + pytest. `Pillow` and `numpy` are already in `requirements.txt` and `tests/python/`
already runs pytest. The harness drives `helix-screen ctl --json` as a subprocess rather than
speaking JSON-RPC directly, so there is exactly one protocol client and no drift surface — the
repo already carries `test_interface_drift_*.cpp` because that class of duplication is
unwelcome. Subprocess cost is ~40ms × roughly 15 commands per test, which is irrelevant at
this scale.

This is not a second harness. All 70+ files in `tests/shell/` test shell scripts — installer,
launcher, packaging, platform detection. None drive the app. UI driving has no existing
coverage in any language.

```
tests/ui/
  conftest.py          # fixtures: helix_app (session-scoped), artifacts (function-scoped)
  helix/app.py         # HelixApp
  helix/goldens.py     # capture / compare / accept
  goldens/             # PNG corpus
  test_*.py
```

`HelixApp` boots `--test --skip-wizard --remote --remote-socket <private path>` and polls
`ping` until responsive. It exposes `navigate`, `click`, `ls`, `text`, `geom`, `get`, `set`,
`wait_idle`, `freeze`, `reset`, `screenshot` (returns a Pillow image), and `log`, plus one
escape hatch — `app.ctl(*args) -> dict` — so a newly added server command is usable from tests
before anyone writes a typed wrapper.

### Failure diagnostics

On any test failure the fixture dumps a screenshot, `log -n 200`, and `pwd` + `ls` into a
per-test artifact directory. A bare `assert False` diagnoses nothing; a PNG plus the app's own
log tail usually is the whole diagnosis. This is the feature that makes the harness actually
replace the manual loop rather than merely automate it.

### Golden mechanics

- Naming: `tests/ui/goldens/<test_name>[__<variant>].png`.
- Comparison is **exact** (`numpy.array_equal`). Freeze is what makes that affordable.
- On mismatch: write `<name>.actual.png` and an amplified `<name>.diff.png` into the artifact
  directory, and fail with the paths.
- A missing golden **fails**. It is not auto-created — a silently generated golden asserts
  nothing. `pytest --accept-goldens` is the only way to write one.
- Size (800x480, 480x320) and theme (dark, light) are pytest params, so variants are
  parameterizations of one test rather than copy-pasted files.

The `docs/images/` corpus is explicitly **not** reused as goldens. Doc screenshots should
change whenever the UI improves; regression goldens should not. Merging those two meanings
trains the owner to reflexively accept every diff.

### Initial corpus

Seed from the tokens already in `scripts/screenshot-recipes.sh` — that navigation is written
and debugged. Grow toward the full `list_components` registry from there.

## Error handling

| Condition | Behavior |
|---|---|
| `ctl --json` exits non-zero | Raise `HelixCtlError` carrying the JSON-RPC error message. |
| Boot never becomes responsive | Fail the session fixture after a timeout, with the app's stderr attached. |
| App dies mid-test | Detected on process poll; surface the last log lines rather than a socket error. |
| `wait_idle` times out | Fail with the counter values that were still nonzero, not a bare timeout. |

## Risks

**Golden portability.** Pixel goldens are sensitive to the machine that produced them —
renderer, font rasterization, library versions. Goldens captured on a desktop will not match a
GitHub Actions runner, and discovering that empirically costs a week. Mitigation: visual
regression stays **local-only** initially. CI runs the driving tests plus a `wait_idle`-gated
smoke pass. When visual regression should gate PRs, generate and compare goldens inside the
same container — the existing cross-build Docker images already provide a fixed environment.

**`wait_idle` enumeration gaps.** Accepted and documented above; the frame-hash gate is the
backstop for the screenshot path. Logic tests that depend on an unseen async source will need
an explicit `wait_for` on a subject.

**Golden churn.** Mitigated by `--target` widget crops and by the fail-on-missing rule. If
churn still becomes routine, that is the signal to narrow the corpus, not to loosen the diff.

## Phasing

1. `--json`, then the Python harness skeleton with `HelixApp` and failure diagnostics.
   Verifiable on its own: port test-navigation.sh to a real test.
2. `wait_idle` + `freeze`/`unfreeze`. Removes every sleep from phase 1.
3. `text` and `reset`. Unblocks meaningful assertions and session-scoped reuse.
4. `screenshot --stable --target` + `goldens.py` + the seed corpus.
5. Tier 2 commands as the tests demand them.
