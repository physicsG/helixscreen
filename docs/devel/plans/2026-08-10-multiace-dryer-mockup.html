Snapmaker U1 + multiACE — design memo

Drying the ACE from the environment panel

HelixScreen already has the whole dryer UI — readout, progress bar, temperature and duration inputs, start/stop — in ams_environment_overlay.xml. It has never appeared on this printer for one reason: no Snapmaker backend reports a dryer, so get_dryer_info() answers supported = false and the panel shows its "no dryer" branch. The ACE has one, and reports it live.

Screens are 1:1 at 480 × 320 and self-measure on load. Live values from the ACE 2 Pro at 192.168.2.242: 31 °C, 35 % RH, dryer_status.status = "stop".

!

The constraint that shapes this

Read this before designing anything

ACED__Dry_Start_0..3 takes no parameters — multiACE's own macro table says "uses config settings". Temperature and duration live in dryer_temp / dryer_duration in multiACE's config file, with a max_dryer_temperature safety cap. There is no G-code to set them.

So the existing panel's temperature and duration inputs cannot be honoured on this backend. Showing them editable and quietly ignoring the values is the one option that must not ship.

Everything else the panel wants is published, per ACE: dryer_status {status, target_temp, duration, remain_time}, plus temp and humidity. multiACE additionally has an auto-dry feature HelixScreen's DryerInfo does not model at all: auto_dry {enabled, rh_start, rh_end, temp, master, add_time} — start drying when humidity crosses rh_start, stop at rh_end.

A

Idle, and drying

The proposal: keep the existing panel, drop the two inputs this backend cannot honour, and state the configured values as fact instead. The unit chips at the top pick which ACE — a 1-unit rig shows one chip and it is not interactive.

B

Several ACEs

Up to four. The panel is per unit, so the chips select which one and everything below follows. ACED__Dry_Stop stops the current ACE, so selecting a unit has to also make it current — otherwise Stop would act on whichever ACE happened to be active.

Two calls I'd like you to make

The temp / duration inputs — drop them, or keep them and write config?
Mocked above as read-only, which is honest and small. The alternative is for HelixScreen to edit multiACE's config file and restart Klipper to apply — a much bigger, much more invasive feature, and one that fights multiACE for ownership of its own config. I would drop them here and leave the config where it is.
Auto-dry — display only, or a toggle?
Shown display-only above. multiACE's macro table lists no auto-dry command, so a toggle would need the same config-writing machinery as the point above. Worth confirming: if ACED__ has an undocumented auto-dry macro I have not found, a toggle is easy.

What it takes either way: AmsBackendMultiAce::get_dryer_info(unit) mapping the parsed dryer_status onto the existing struct, start_drying() emitting ACED__Dry_Start_<n> and stop_drying() emitting ACED__Dry_Stop, plus a supports_fan_control = false and honest min/max from the config cap. The panel itself already exists and needs no new screen.
